Tolka is designed so that translation text is processed in memory and is not written to our database, logs or caches by the translation pipeline. There are documented exceptions, described below.

---

## Translation pipeline

For the translation pipeline:

- **Request text** (`text` field) is processed in memory for the duration of the API request. The pipeline does not write it to a database, a log or a cache.
- **Translation output** (`translation`, `back_translation`) is returned in the response. The pipeline does not store it.
- **Session tokens** are encrypted opaque blobs. The server holds the encryption key but not the session contents; session state round-trips through the client.

Translation text is not part of what Tolka stores about your organisation, apart from the exceptions below.

---

## What Tolka stores

| Data | Purpose | Retention |
|------|---------|-----------|
| Organisation metadata, hashed API keys | Account and authentication | Not yet set |
| Daily usage counts per organisation (no text) | Usage accounting and limits | Not yet set |
| Request audit log: request ID, organisation, endpoint, status code, latency, model label, risk level, error code (no text) | Security and audit evidence | Not yet set |
| Clinician flags (optional feature): the source text, translation, back-translation and note a clinician submits; scoped to your organisation; not available to templates-only accounts | Quality feedback | Not yet set |

Retention periods are not yet defined. We will publish them here once they are.

<Aside type="caution" title="Exceptions to 'no text stored'">
Clinician flags store the text a clinician chooses to submit. Separately, contact details sent through the demo request form on tolka.health are held by our website host; they are not translation text.
</Aside>

## Where Tolka runs

Tolka's API and Console run on Fly.io in Frankfurt, Germany. Pre-written phrase lookups and refusals make no call to any translation provider.

Free-text translation uses third-party language-model providers. Their data-residency terms have not yet been established, and free-text translation is currently switched off for all accounts. We make no claim that all processing stays in the EU.

## Data flow

```
Client (browser / app)
        │
        │  HTTPS
        ▼
Tolka API (Frankfurt)
        │
        ├── Phrase library lookup
        ├── Translation by a provider (when enabled; residency not yet established)
        ├── Back-translation and risk check (when enabled)
        │
        ├── Audit log: request ID, organisation, endpoint, status, latency, risk level
        │         (no text, no translation)
        │
        └── Response returned to the client
```

## GDPR role

Tolka acts as a **data processor** on behalf of your organisation (the data controller) when you use the API with patient text:

- You are responsible for having a lawful basis for the processing (typically Article 9(2)(h), healthcare purposes).
- Tolka's obligations as processor are set out in a Data Processing Agreement. See [Compliance & Trust](/about/compliance/).
